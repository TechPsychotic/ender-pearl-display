# The Pi software

## Files
| File | Role |
|---|---|
| `pi/display/glass_main.py` | entry point:
  - **connect:** finds UART3, gets the link to 921600 with replies on, stops the firmware's boot loop;
  - **boot animation:** plays the rest of it;
  - **main loop:** runs the app, reads the knob, writes the live frame for the browser |
| `pi/display/glass/app.py` | the UI: screens, menus, element cache, background API calls, sleep/wake |
| `pi/display/glass/canvas.py` | drawing on top of TJC instructions (`TjcCanvas`): panels, text, bars, flow control, frame recording |
| `pi/display/glass/theme.py` | colours, font roles, sizes. Shared with the laptop mockup renderer |
| `pi/display/glass/fake.py` | a fake API with plausible data, for mockups and tests |
| `pi/display/glass/manifest.json` | picture and font ids in the firmware (generated by `design/build_assets.py`) |
| `pi/display/glass/metrics.json` | glyph widths per font (generated by `design/build_metrics.py`) |
| `pi/display/glass/icons.json` | icon name → character in the icon font |
| `pi/display/tjc.py` | TJC instruction builders, error codes, serial upload |
| `pi/display/flash.py` | flash a `.tft` (or the stock one) over UART3 |
| `pi/display/link.py` | find UART3's tty by device-tree address |
| `pi/display/gpio.py` | GPIO through the kernel character device: knob inputs, quadrature decoder, an output (beeper test) |
| `pi/display/bench.py` | raw TJC instructions from stdin, replies as JSON lines (the desktop controller's Bench; the display service must be stopped) |
| `pi/display/tjc_hello.py` | first-light test for a fresh firmware: text, fills, a circle, a bar |
| `pi/display/protocol.py`, `sniff.py`, `demo.py`, `gallery.py`, `ui.py` | the stock-protocol tools ([02](02-stock-protocol.md)) |

Requirements: Python 3, `pyserial`. Nothing else on the Pi. The laptop design tools also need Pillow.

## Knob
| Action | Effect |
|---|---|
| turn | move the focus, or change a value |
| press | select / confirm |
| hold ≥ 0.8 s | back / cancel |

`KNOB_DIR` in `glass_main.py` flips the direction. The default turns clockwise to move up a list.

## Screens
**Home** (temperatures, status line, tiles) → **Print** (files on the Pi with print time, SD card, queue,
file details with a 3D preview, start confirmation) · **Prepare** (home, move axes, jog, preheat, cool down,
filament load/unload) · **Control** (display, motion, temperature/PID, calibration prints, store/restore settings,
info) · **Level** (bed mesh, auto level, Z offset).

While printing: **Printing** (progress by time, time left, finish time, live 3D preview, temperatures, fan,
speed and flow) → **Tune** (speed, flow, fan, temperatures, Z babystep) · **Stop** (skip an object, stop).
The full list with every item is in [design/MENUS.md](../design/MENUS.md). Every screen as rendered:
[images/screens.png](images/screens.png).

Anything that moves the printer, heats or changes stored settings asks for confirmation first. Items that need an
idle printer are greyed out while printing.

## Talking to the host
The app never touches the printer's serial port. Everything goes through the host project's HTTP API
(`http://127.0.0.1:8080`, token from `ui/token.txt`). The screen and the browser share one state, and every safety
check lives in the server. Calls made by `glass_main.Api`:

| Call | Used for |
|---|---|
| `GET /api/state` | everything live: temperatures, job, progress, queue, filament, alerts |
| `GET /api/display/files`, `/api/plan` | file list with print times, file details |
| `GET /api/display/preview` / `model` / `objects` | 3D preview paths (prebuilt and cached by the server) |
| `POST /api/print`, `/api/stop`, `/api/cmd`, `/api/printer` | start, stop, pause/resume, tune, motion, heaters, filament |
| `GET/POST /api/queue`, `GET /api/settings`, `POST /api/calibrate`, `POST /api/filament` | queue, printer settings, calibration prints, loaded filament |
| `GET/POST /api/display/config` | wallpaper, brightness, sleep time, clock, messages and "show" requests from the web UI |

And towards the app: `POST /api/display/input` (`turn` ±n, `press`, `long`) reaches `glass_main.py` as a datagram on
`127.0.0.1:47321` and works exactly like the real knob (the desktop controller uses it).

`server/display_api.py` is the server side of the `/api/display/*` endpoints. It's taken from the host project and
uses its internals (G-code plans, the jobs folder), so treat it as a reference implementation. To use the display with
another host (OctoPrint, Moonraker…), replace `glass_main.Api` with calls to that host's API: the app only needs the
methods listed above.

## Running it as a service
`server/install_display.sh` installs `server/ender-loop-display.service` as a systemd **user** service:
- **Start-up:** it starts at boot (the user needs lingering enabled) and restarts on failure. The log goes to
  `out/display.log`.
- **Ordering:** it `Wants=` the web server's unit and starts after it. The server's unit must **not** also say
  `After=default.target`: together they form an ordering cycle, and systemd silently drops the server's start job.
- **Settings before the server:** at boot the app reads its saved settings straight from `out/display_config.json`
  if the server isn't answering yet, so the wallpaper and brightness come back immediately.

## Behaviour worth knowing
- **Sleep:** after the set time with no input, `dim=0` turns the backlight off. Any of these wakes it:
  - the knob (the first turn only wakes it);
  - a print starting or finishing;
  - a message or a "show" request from the web UI.

  While printing it stays awake.
- **Progress** is time-based: elapsed ÷ (elapsed + remaining), capped at 99 % until the job reports done. Counting
  G-code lines read 100 % with several small top layers still to go.
- **Alerts** from the print queue show as text on the home status line until acknowledged.
- **Restarting the display service is safe during a print:** the print job belongs to the web server's service.
